The experiment

One dataset, three engines, three scales

Every run below fits the same problem: predict a binary outcome from 50 numeric features, on 200,000 → 10,000,000 → 20,000,000 rows of synthetic data with a known logistic relationship (y ~ Bernoulli(sigmoid(Xβ + noise))) — the noise term keeps the ceiling honest, so no model gets to be perfect.

Three fitting engines see the exact same train/test split each time:

Logistic Regression (scikit-learn's lbfgs solver) — the textbook default. SGD Classifier — the one usually recommended once data gets "too big." LPM, a Linear Probability Model — plain linear regression pointed at a 0/1 label, the econometrician's shortcut. All three ran on one 8-core, 17GB laptop — deliberately under-powered next to the 32–64GB cloud machine this experiment is headed for, so it doubles as a stress test.

The mechanics

Three ways to fit a line through probability

"Fitting a model" means one thing underneath all three: searching for the coefficients that make a loss function as small as possible. Where they differ is how they search.

Engine 1

Logistic Regression — lbfgs

Models P(y=1) = sigmoid(Xβ) and searches for β by minimizing log-loss.

lbfgs is a quasi-Newton method: alongside the gradient (which way is downhill), it keeps a running estimate of curvature — how the slope itself is changing — built from its last several steps. That extra information lets it aim much further per step than plain gradient descent.

Cost per step: one full pass over every row and every feature. Steps needed here: 7, at every scale tested. Needs: the whole dataset in memory before it can take even one step.
Engine 2

SGD Classifier

Same model as Engine 1 — linear score through a sigmoid — a completely different optimizer.

Instead of the exact gradient over all rows, SGD estimates it from small batches and takes an immediate, noisy step. One epoch = one pass through the data doing many of these cheap updates. No curvature information at all — just slope, guessed from a sliver of the data at a time.

Cost per step: nearly free. Steps (epochs) needed here: 49–63 — run to its own convergence tolerance. The other mode: cap the epoch count and stop on a clock instead of a convergence test — cheaper, but you pay for it in quality (see below).
Engine 3

LPM — Linear Probability Model

Not a different optimizer — a different model. Fits E[y|X] = Xβ directly, with ordinary least squares. No sigmoid anywhere.

OLS has a closed-form solution — solve one linear system and you're done. No iteration, no convergence criterion, no "how many steps." One shot, every time.

Cost: one linear solve, independent of how separable the classes are. The catch: predictions aren't bounded to [0,1] — 15% of test predictions land outside that range in every run here.

Walking downhill with a map

lbfgs doesn't just feel the slope under its feet — it remembers the shape of the last few hills it crossed, and uses that to guess how the terrain curves ahead. On smooth, well-behaved terrain (like this well-conditioned synthetic data), that lets it take a handful of confident, long strides straight to the bottom.

Walking downhill blindfolded, one step at a time

SGD only ever feels the slope right under one foot, guessed from a small patch of ground — no memory of the terrain's shape. Each step is instant, but noisy and short, so it takes far more of them to end up in the same place lbfgs reaches directly.

Why lbfgs wins here

Wall time is a pass count, multiplied

Every one of these algorithms pays the same tax per pass over the data — one matrix multiply touching every row and every feature. What actually decides wall time is how many passes it takes, and that number is a property of the algorithm and the data's conditioning, not of how many rows there are.

lbfgs needed exactly 7 full-data passes at every single scale tested — 200K, 10M, and 20M rows alike. That's the quasi-Newton curvature estimate paying off: on this well-conditioned synthetic data, it converges in single digits regardless of row count. SGD run to its own tolerance needed 63 epochs at 200K, 49 at 10M, 48 at 20M — the count itself barely moves either, it's just pinned roughly seven times higher than lbfgs's, so every pass tax it pays gets multiplied by seven across the board.

Fit time vs. rows, per engine log–log — a straight line means "linear in rows"
The honest caveat: this synthetic dataset is clean and well-conditioned by design — Gaussian features, a genuine linear-logit signal. Real data with correlated or poorly-scaled features can push lbfgs's iteration count up sharply, while SGD's epoch count is comparatively insensitive to conditioning. The crossover point moves per dataset — benchmark on your real data before assuming lbfgs will win.
Rows & features

How the engine changes what "more data" costs

Rows and features don't hit every engine the same way — the exponent on features is where they genuinely diverge.

lbfgs
cost ≈ passes × rows × features
Linear in both. Passes (7 here) stay roughly flat as rows grow — that's what made the 200K→20M scaling near-perfectly linear above.
SGD
cost ≈ epochs × rows × features
Same shape as lbfgs, bigger multiplier. Epoch count is set by how you configure it — tol-based or capped — not by row count.
LPM
cost ≈ rows × features²
Linear in rows, quadratic in features — solving the normal equations means inverting a features×features matrix.

At 50 features, that quadratic term is invisible — 50² is 2,500, nothing for modern linear algebra. It's why LPM's closed-form solve was competitive with (and at 10M rows, faster than) lbfgs's 7 iterations. Push feature count into the thousands, though, and the picture flips: at 5,000 features the quadratic term is 10,000,000 — LPM's "instant" closed form stops being instant, while lbfgs and SGD's linear-in-features cost barely notices.

Memory scales the same way for all three — rows × features × 4 bytes (float32) to hold the feature matrix once. 20M rows × 50 features is 4GB; that arithmetic is exactly what made the data-generation step earlier in this project worth getting right (a memory-mapped writer that never flushed until the end could momentarily hold the entire file's worth of dirty pages in RAM — get the multiplier wrong once, by using float64 or duplicating the array, and 4GB becomes 8 or 16).

Parallelizing SGD

Ray loses at echo scale, wins at target scale

The obvious way to parallelize SGD is to shard the data across workers and sync a gradient after every mini-batch. For a model with 51 numbers to average (50 features + intercept), that's a bad trade: the fixed overhead of serializing, scheduling, and round-tripping through Ray's object store dwarfs the few microseconds of actual compute per step.

What we tested instead is the pattern real distributed-training systems actually use: local SGD with periodic averaging. Shard the data, let each worker train independently for several epochs with zero communication, then average everyone's weights and (optionally) do another round. We ran it at both ends of this experiment's range — 200K rows and the full 20M-row target — on the same 8-core laptop.

At 200K rows, Ray never beat the single-process baseline — the best it managed was 0.51× at 4 workers, i.e. still slower, before falling back to 0.24× at 8 workers as scheduling overhead started competing with actual compute for the same 8 physical cores. The crossover happens fast: by 10M rows Ray is already decisively ahead, and it's actually the best result on this page — 3.81× at 8 workers (57.6s → 15.1s), edging out even the full 20M-row run's 3.31× (122.1s → 36.9s).

Why the crossover happens — and why it doesn't keep climbing: the fixed per-round overhead (serialization, actor scheduling, the object-store round trip) is roughly constant no matter the data size. At 200K rows each worker's local epochs are too cheap for that overhead to be worth paying, so it never wins. Once shards are large enough — somewhere between 200K and 10M rows here — local compute dwarfs that fixed cost and the parallelism pays off in a big way. That the 20M run's speedup is slightly lower than 10M's, not higher, is a reminder that "more rows, more speedup" isn't guaranteed either: 8 workers is still 8 physical cores on one box, and other overheads (larger per-round payloads to serialize and average, memory pressure) can start eating back into the gains once shards get large enough.

The rule of thumb this confirms: reach for Ray's local-SGD-with-averaging once each worker's shard is big enough that local training time clearly exceeds Ray's per-round overhead — on this hardware, that line sits somewhere between 200K and 10M rows. Below it, the single-process baseline wins outright; above it, expect a strong, fairly stable multi-x speedup, not one that keeps growing indefinitely with row count.

Takeaways

When to reach for each

lbfgs
Data fits comfortably in RAM and you want the closest thing to an exact answer with the least tuning. On well-conditioned data, it converges in single-digit passes regardless of row count — the default for a reason.
SGD, capped
You have a hard time budget, not a hard quality bar, and rows are too many for full-batch passes to stay cheap. Tune the epoch cap against a validation set — "just run a few epochs" is a dial, and this experiment shows it costs real accuracy if set too low.
LPM
You want a fast closed-form baseline, directly interpretable coefficients, or streaming/partial updates — and you can live with predictions occasionally landing outside [0,1] (15% of test rows, here). Stops being "instant" once feature count climbs into the thousands.
Ray
Rows in the millions or beyond, with idle cores to spend. Use local-SGD with periodic averaging, not per-step gradient sync — it delivered 3.3–3.8× at 10M and 20M rows on 8 cores here (down to 15–37s from 58–122s), but was never worth it at 200K rows on the same machine. Check which side of that line your data sits on before reaching for it.

Methodology. Synthetic data, 50 features, generated from a known logistic relationship with an explicit noise term. All three engines saw the same train/test split at each scale. Timings measured with time.perf_counter() around .fit() only; memory via process RSS delta. Run on one 8-core / 17GB laptop — meaningfully smaller than the 32–64GB cloud target this experiment is built for, so treat exact seconds as directional, not a guarantee on different hardware.
